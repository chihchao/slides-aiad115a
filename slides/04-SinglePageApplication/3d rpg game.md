# 3D RPG 專題規劃（教師用）

## 實作可行性評估

**結論：整體可行，但必須控制範圍。** React SPA、Firebase、PWA 都是本單元已教過的技術；Three.js 在瀏覽器直接執行；Agent 擅長撰寫移動、碰撞、對話與任務狀態等邏輯。主要限制在素材、離線快取與手機效能。

| 面向 | 評估 | 說明 |
|---|---|---|
| 3D 渲染 | 可行 | Three.js（建議搭配 React Three Fiber）不需另外安裝引擎 |
| Agent 撰寫程式 | 可行 | 遊戲邏輯與畫面分離後，Agent 與測試都容易處理 |
| 整合 SPA / Firebase | 可行 | 沿用 React、Auth、Firestore、Hosting；存檔可跟著帳號走 |
| PWA 離線 | 有條件 | 模型與音檔較大，需設計快取；Workbox 預設只預先快取 2 MiB 以下的檔案 |
| 3D 模型與音效 | 最大限制 | Agent 無法操作 Blender 建模；以幾何體與授權明確的免費素材（如 Kenney、Quaternius，CC0）為主 |
| 手機操作 | 有條件 | 需觸控搖桿，且效能要用實機測試 |
| 自動化測試 | 部分可行 | 遊戲邏輯可單元測試；3D 畫面與「好不好玩」仍需真人試玩 |

### 主要風險與對策

| 風險 | 原因 | 對策 |
|---|---|---|
| 範圍失控 | 3D 遊戲容易越想越大 | 階段一寫明「必做／可選／不做」；建議一張地圖、三到五個任務 |
| 素材卡關 | Agent 無法建模、作曲 | 先用方塊與膠囊體；之後以免費素材取代；記錄來源與授權 |
| 離線快取失敗 | 大型檔案超過預設快取上限 | 調整大小上限或使用執行時快取，並以離線模式實測 |
| 舊版快取 | Service Worker 提供舊畫面 | 新版本出現時提示重新載入；部署後用無痕視窗驗證 |
| 手機效能不足 | 模型面數、貼圖過大 | 限制面數與貼圖尺寸，用實機測試 |
| iOS 沒有聲音 | 需使用者操作後才能播放 | 設計「開始遊戲」按鈕，首次點擊後再啟動音訊 |
| 測不到 3D 畫面 | 畫面在 canvas 中 | 邏輯與畫面分離；將任務與道具狀態公開給測試讀取 |

### 建議技術棧

Vite + React + TypeScript、three + @react-three/fiber + drei、zustand（遊戲狀態）、Vitest + Playwright（測試）、Firebase Auth / Firestore（選用存檔）、vite-plugin-pwa、Firebase Hosting。不引入物理引擎或遊戲引擎，碰撞以簡單的圓形與方塊判斷處理。

### 對下方提示詞的調整

- **階段一**：原提示詞的平台只寫 Three.js，已改為 React SPA、Firebase Hosting、PWA。
- **階段四**：加入 React Three Fiber 技術方向；存檔規則（何時存檔、重新開始是否清除存檔）若採用，需在階段二規格中先決定。
- **階段六**：加入 PWA 任務（離線、安裝、快取更新）與手機音訊驗證。
- **技能名稱**：已對照 [mattpocock/skills](https://github.com/mattpocock/skills)，grill-me、grill-with-docs、to-tickets、implement、tdd、diagnosing-bugs、code-review 皆存在。

以下將前三階段統一安排為：**學生與 AI agent 討論設計，由學生確認決策，再整理成 `.md` 規格檔**。這三個階段不撰寫遊戲程式，成果將作為後續開發 agent 的實作依據。

提示詞中的 `【】` 請由學生填寫；第二、三階段需提供前階段的檔案，讓 AI 延續既有設計。

## 第一階段：世界觀與故事設計

### 階段說明

確定遊戲的主題、玩家角色、故事背景與目標，回答「玩家是誰、為什麼冒險、會經歷什麼，以及如何結束」。

學生需比較 AI 提出的方案並做出選擇，將故事控制在製作時間與能力可負擔的範圍內。

### 學生交付成果

**主要檔案：`01_世界觀與故事.md`**

| 必要內容 | 說明 |
|---|---|
| 專題基本資料 | 遊戲名稱、目標玩家、預計遊玩時間、開發期限與執行平台 |
| 遊戲核心概念 | 一句話介紹、玩家目標、希望帶給玩家的體驗或學習目標 |
| 製作範圍 | 必做內容、可選內容與本次不做的內容 |
| 世界觀 | 時空背景、世界規則、主要衝突 |
| 角色設定 | 主角與 NPC 的編號、名稱、身分、動機及故事功能 |
| 故事流程 | 開場、主要事件、高潮、結局及其發生條件 |
| 故事文字 | 開場文字、關鍵對話與結局文字 |
| 設計決策紀錄 | 至少兩項採用、修改或拒絕 AI 建議的理由 |
| 待確認問題 | 尚未決定、需要後續討論或技術驗證的事項 |

**驗收重點：**其他人閱讀文件後，能清楚理解遊戲的故事、玩家目標與製作範圍。

### 可直接使用的提示詞

```text
你是我的 3D RPG 遊戲企畫協作 agent。
現在進行第一階段「世界觀與故事設計」。

本階段只討論與整理設計，不撰寫遊戲程式、不建立可執行原型。
成果將交給後續 AI agent，作為撰寫程式的依據。

【我的專題條件】
- 初步遊戲構想：
- 目標玩家：
- 希望帶給玩家的體驗或學習目標：
- 預計遊玩時間：
- 製作期限：
- 我的程式與建模經驗：
- 執行平台與裝置：以 React + Three.js 製作的 SPA 網頁遊戲，部署在 Firebase Hosting 並做成可安裝的 PWA，【填寫裝置】
- 其他限制：

【討論方式】
1. 先閱讀我的條件，每次最多問三個關鍵問題，等我回答後再繼續。
2. 資訊足夠後，提出兩個可行的故事方向，比較特色、製作難度與素材需求。
3. 由我選擇或修改方向，再逐步完成設計，不要一次替我決定全部內容。
4. 若構想超出製作範圍，請提出縮減方案並說明理由。
5. 不確定的內容標示「待確認」，不要自行當成已確認規格。

【需要完成的設計】
1. 遊戲名稱與一句話介紹。
2. 玩家目標與預期體驗；若有學習目標，說明它如何出現在玩家行動中。
3. 必做、可選及本次不做的內容。
4. 世界背景、世界規則與主要衝突。
5. 主角與 NPC 的身分、動機及故事功能。
6. 開場、主要事件、高潮與結局，以及發生條件。
7. 開場文字、關鍵對話與結局文字。
8. 我的設計決策紀錄與待確認問題。

【文件要求】
- 討論中先呈現草案，經我確認後再整理定稿。
- 角色使用固定編號，例如 PLAYER01、NPC01。
- 後續階段需延續相同編號與名稱。
- 使用 Markdown 標題、表格與條列，讓開發 agent 容易閱讀。
- 請檢查角色動機、故事因果及製作範圍是否合理。
- 若能操作檔案，建立「01_世界觀與故事.md」。
- 若不能操作檔案，輸出可直接儲存為該檔案的完整 Markdown。

請先從確認我的專題條件開始。
```

## 第二階段：關卡與互動機制

### 階段說明

把第一階段的故事轉成玩家能操作的任務，明確定義「什麼情況可以做、玩家怎麼做、做了會發生什麼，以及怎樣算完成」。

此階段要讓開發 agent 能依規格實作，特別需要寫清楚任務順序、遊戲狀態、錯誤回饋與避免卡關的方法。

### 學生交付成果

**主要檔案：`02_關卡與互動規格.md`**

| 必要內容 | 說明 |
|---|---|
| 核心遊玩循環 | 例如探索 → 對話 → 蒐集 → 解謎 → 完成任務 |
| 操作方式 | 移動、互動、取消、選單等輸入與對應行為 |
| 任務總表 | 任務編號、名稱、目的、前置任務與解鎖關係 |
| 各任務詳細規格 | 觸發條件、玩家行動、成功條件、錯誤回饋與完成結果 |
| 互動物件規格 | NPC、道具、機關的用途、操作及使用限制 |
| 遊戲狀態與規則 | 任務狀態、道具取得與消耗、重複互動的處理 |
| 提示與恢復機制 | 提示內容、重試方法、失敗及重新開始的處理 |
| 驗收條件 | 每個任務可實際檢查的預期行為 |
| 紙上試玩與決策紀錄 | 模擬流程發現的問題、修改及理由 |
| 待確認問題 | 尚未決定或需要技術驗證的事項 |

任務流程圖可用 Markdown 內的 Mermaid 或文字箭頭呈現，並附文字說明。

**驗收重點：**每個任務都有清楚的觸發條件、操作、結果與驗收方式，整體流程能從開始走到結局。

### 可直接使用的提示詞

```text
你是我的 3D RPG 關卡與互動設計協作 agent。
現在進行第二階段「關卡與互動機制」。

本階段只設計規則與整理文件，不撰寫遊戲程式。
成果將交給後續 AI agent 實作。

【輸入資料】
請閱讀我提供的「01_世界觀與故事.md」。
若無法存取檔案，請告訴我需要貼上哪些內容，不要假設已讀取。

【討論方式】
1. 先摘要既有故事、玩家目標與製作範圍，確認你的理解。
2. 找出會影響任務設計的缺漏，每次最多問三個問題，等我回答後再繼續。
3. 提供可行選項與建議，由我決定主要玩法。
4. 沿用第一階段的編號、名稱與設定。
5. 若需修改第一階段，先指出原因，由我確認後同步更新相關內容。
6. 不加入超出既定範圍的功能；未決事項標示「待確認」。

【需要完成的設計】
1. 核心遊玩循環。
2. 操作方式與對應行為。
3. 任務總表及任務之間的前置與解鎖關係。
4. 每個任務的詳細規格：
   - 任務編號、名稱與目的。
   - 前置條件與觸發方式。
   - 玩家行動與相關 NPC、物件、場景。
   - 成功條件。
   - 錯誤操作、未滿足條件及失敗時的回饋。
   - 提示、重試與避免卡關的方法。
   - 完成後的道具、獎勵、狀態變化與後續任務。
5. NPC、道具與機關的互動規則。
6. 任務狀態、道具取得與消耗，以及重複互動的處理。
7. 遊戲結束與重新開始時的規則。
8. 每個任務的驗收條件，使用：
   「在什麼前提下 → 玩家做什麼 → 應出現什麼結果」。

【流程檢查】
請和我進行一次紙上試玩，由你描述情境，我選擇玩家行動，
再依規則檢查結果。

至少檢查：
- 正常完成任務。
- 尚未接受任務就操作物件。
- 未取得必要道具就嘗試交付。
- 重複拾取、對話或領取獎勵。
- 任務順序錯誤。
- 遊戲結束後重新開始。

若某種情況不適用，請說明原因。
請記錄發現的問題及經我確認的修改。

【文件要求】
- 討論完成、經我確認後，整理為「02_關卡與互動規格.md」。
- 任務使用 Q01、Q02 等固定編號；物件使用 ITEM01 等固定編號。
- 以表格、條列及流程圖呈現，重要規則必須有文字說明。
- 包含我的設計決策、紙上試玩結果與待確認問題。
- 若能操作檔案，建立 .md 檔；否則輸出完整 Markdown。

請先閱讀第一階段文件，整理你的理解與需要確認的問題。
```

## 第三階段：3D 場景與遊戲 UI

### 階段說明

將故事與任務轉成具體的空間及畫面規格，回答「玩家在哪裡、往哪裡走、能看見什麼，以及畫面如何提示操作」。

**這裡是規劃 3D 場景，不是建立 3D 場景。** 可以用文字、俯視配置圖與 UI 草圖表達；實際建模及程式實作留到後續階段。

### 學生交付成果

**主要檔案：`03_場景與UI規格.md`**

| 必要內容 | 說明 |
|---|---|
| 視覺風格 | 色彩、造型、氣氛與參考方向 |
| 地圖配置 | 場景區域、出生點、道路、障礙、NPC 與任務物件位置 |
| 空間尺度 | 尺度基準、相對距離、道路寬度與物件尺寸 |
| 鏡頭與移動規則 | 視角、跟隨方式、移動範圍及碰撞規則 |
| 互動提示 | 可互動的距離、對象判定及提示文字 |
| UI 規格 | 各畫面元素、位置、文字、按鈕行為與顯示條件 |
| 素材需求清單 | 模型、圖像、音效與音樂的編號、用途及規格 |
| 驗收條件 | 場景、動線、鏡頭、UI 與目標裝置的檢查標準 |
| 設計決策與待確認問題 | 選擇理由、尚未決定及待技術驗證事項 |

**附圖：**地圖配置圖、UI 線框圖。可直接在 Markdown 中示意；若使用獨立圖片，放在 `assets/design/` 並以相對路徑引用。

**驗收重點：**開發 agent 能依文件安排場景與介面，且每個任務需要的角色、物件及提示都有對應位置。

### 可直接使用的提示詞

```text
你是我的 3D RPG 場景與 UI 設計協作 agent。
現在進行第三階段「3D 場景與遊戲 UI」。

本階段只完成設計文件與示意圖，
不撰寫遊戲程式、不建立可執行原型、不製作正式 3D 模型。

【輸入資料】
請閱讀：
- 01_世界觀與故事.md
- 02_關卡與互動規格.md

若無法存取檔案，請告訴我需要貼上哪些內容。

【討論方式】
1. 先整理任務需要的區域、NPC、物件與畫面。
2. 找出缺少或矛盾的設計，每次最多問三個問題，等我回答後再繼續。
3. 提出可行的場景與 UI 方案，比較可讀性、製作難度與操作便利性。
4. 由我確認主要設計，並沿用既有編號與名稱。
5. 不自行增加新任務或新玩法。
6. 設計數值可以先提出建議，但須區分「已確認」與「待測試調整」。

【需要完成的場景設計】
1. 視覺風格、主要色彩、造型與氣氛。
2. 場景區域、出生點、NPC、任務物件、道路、障礙與終點。
3. 地圖俯視示意及圖例。
4. 尺度基準、區域相對位置、距離、道路寬度與主要物件尺寸。
5. 鏡頭視角、跟隨方式與可視範圍。
6. 玩家移動範圍、不可通行區及碰撞規則。
7. 互動距離、同時靠近多個物件時的選擇規則與提示。
8. 引導玩家辨認道路、任務目標與可互動物件的方法。

【需要完成的 UI 設計】
請列出遊戲實際需要的畫面，例如開始、遊玩、對話與結束畫面。
每個畫面都要說明：
- 出現與關閉的條件。
- 元素名稱、位置及排列。
- 顯示文字或文字來源。
- 按鈕與輸入操作，以及操作後的結果。
- UI 開啟時，角色移動與其他互動是否暫停。
- 不同目標螢幕尺寸下的配置。
- 文字可讀性與不只靠顏色傳達資訊的做法。

【素材與驗收】
1. 建立模型、圖像、音效與音樂需求清單。
2. 列出素材編號、用途、出現位置、需求規格與預計取得方式。
3. 尚未取得的素材標示「待製作」或「待取得」，不要聲稱已完成。
4. 為場景動線、鏡頭、互動提示及 UI 撰寫可檢查的驗收條件。
5. 檢查每個任務需要的場景、物件與 UI 是否都有安排。

【文件要求】
- 經我確認後，整理為「03_場景與UI規格.md」。
- 用文字、表格與示意圖描述，不能只靠圖片表達重要規則。
- 若有獨立圖片，放在 assets/design/，以相對路徑引用。
- 包含我的設計決策與待確認問題。
- 若能操作檔案，建立 .md 檔；否則輸出完整 Markdown。

最後請交叉檢查三份文件，列出：
- 名稱、編號或規則不一致的地方。
- 開發前必須補齊的資訊。
- 可以留到實作時驗證的項目。

本階段結束後仍不要開始寫遊戲程式。
請先閱讀前兩階段文件，整理場景與 UI 的需求。
```

```text
        └── UI線框圖.png
```

其中圖片依實際需要提供。**學生的責任是確認設計與說明選擇理由；AI agent 的責任是協助釐清、檢查一致性並整理成可實作的規格。**


---
**適合，尤其是第二階段的關卡與互動機制；建議搭配課堂規則與 Markdown 交付要求使用。**

我查看了儲存庫目前的內容：[grill-me](https://github.com/mattpocock/skills/blob/main/skills/productivity/grill-me/SKILL.md) 會呼叫 [grilling](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)，核心做法是：

- 把構想拆成有先後依賴的設計決策。
- 分輪提問，每題提供建議答案，等待使用者回答。
- 根據回答繼續追問，直到雙方對設計有共同理解。

這很符合你的目的：讓學生透過討論，把模糊構想整理成能交給開發 agent 的規格。

### 前三階段怎麼搭配？

| 階段 | 適合追問的問題 | 使用建議 |
|---|---|---|
| **1. 世界觀與故事** | 主角為什麼冒險？玩家有什麼目標？結局如何回應主要衝突？ | 先讓學生自由提出構想，再用 grill-me 檢查因果、動機與範圍，避免太早限制創意 |
| **2. 關卡與互動機制** | 任務如何觸發？沒有道具怎麼辦？重複互動會發生什麼？如何避免卡關？ | **最適合使用**，能補齊容易被忽略的條件、例外及驗收方式 |
| **3. 3D 場景與 UI** | 玩家如何找到目標？提示何時出現？對話時能否移動？多個互動物件靠近時如何選擇？ | 搭配地圖與 UI 草圖討論，將視覺構想轉成明確行為規格 |

### 建議調整的三個地方

**第一，限制每輪問題數量。** 原版會在同一輪詢問目前所有可以回答的問題，對初學者可能負擔太大。課堂上建議每輪最多三題，先處理會影響後續設計的重要決策。

**第二，要求學生解釋理由。** 原版會讓「回答是」代表接受建議，學生容易一路同意。可以要求學生在重要決策中補上一句理由，並允許回答「我不知道，請先解釋或舉例」。

**第三，另外指定文件產出。** grill-me 的核心是訪談與釐清，**本身沒有規定要產出你需要的三份 `.md` 規格**，因此仍要保留前面各階段的內容清單與交付要求。

### 可加在前三階段提示詞前的共用指令

以下是建議的**課堂調整版規則**，不是原版 skill 的逐字內容：

```text
請使用 grill-me skill 協助我釐清本階段的設計，
並配合以下課堂規則：

1. 先閱讀本階段要求與既有文件，只討論本階段的範圍。
2. 每輪最多問三個問題，優先處理會影響後續設計的重要決策。
3. 有先後依賴的問題，等前一項決定後再問。
4. 每題提供可理解的選項、建議與理由，但讓我做最後決定。
5. 重要決策請我說明選擇理由，不要只讓我回答「是」。
6. 如果我不懂，先解釋或舉例，再讓我選擇。
7. 已在文件中明確記載的資訊，請先讀取，不要重複詢問。
8. 不擴大專題範圍；非必要細節或需要實作才能驗證的事項，
   記錄為「待確認」或「待技術驗證」。
9. 當本階段必要規格已齊全，請摘要已確認決策與剩餘問題，
   讓我確認，不要無限追問。
10. 經我確認後，依本階段交付要求建立對應的 Markdown 檔，
    保留設計決策紀錄及待確認事項。
11. 本階段不撰寫遊戲程式、不建立可執行原型。
```

因此，建議採用的流程是：

**學生提出初步構想 → grill-me 分輪追問 → 學生做決策並說明理由 → 確認設計摘要 → 產出該階段 `.md` 規格。**

原先的三階段提示詞仍然保留，負責界定「要討論什麼、要交付什麼」；grill-me 則負責改善「如何追問、如何釐清」。


---

可以，這樣課程流程會更清楚：**前三階段完成設計規格，第四至第六階段直接以 agent 製作、測試與部署遊戲，不再要求各階段繳交文件。**

原本第四階段只做模型、第五階段只做聲音的安排，建議改成以下方式。模型與音效會在實作過程中依需求加入。

| 階段 | 學生與 agent 的工作 | 完成判準 |
|---|---|---|
| **4. 技術規劃與遊戲實作** | 讀取前三份規格、確認技術棧，逐步建立玩法、場景、模型、UI 與聲音 | 遊戲能從開始玩到結束 |
| **5. 測試與修正** | 執行自動化測試、實際試玩、修正錯誤及操作問題 | 主要流程通過測試，沒有阻礙完成遊戲的問題 |
| **6. 部署與上線驗證** | 建置、部署，檢查正式網址上的操作與素材載入 | 其他人能透過網址開啟並完成遊戲 |

**不必另外繳交技術報告或測試報告**；agent 可以把工作紀錄保留在專案中，供後續開發與除錯使用。學生則在操作過程中確認設計、試玩並提出修改需求。

### 第四階段：技術規劃與遊戲實作

先讓 agent 說明技術選擇，再做出一條完整可玩的流程，之後逐步擴充。避免一次產生全部程式，直到最後才發現玩法不符合規格。

**學生提示詞**

```text
現在開始第四階段：技術規劃與遊戲實作。

請閱讀：
- 01_世界觀與故事.md
- 02_關卡與互動規格.md
- 03_場景與UI規格.md

本階段直接在專案中實作，不需要產出供我繳交的階段報告。

請先檢查目前專案與工具環境，再完成以下工作：

1. 找出會影響實作的規格缺漏與矛盾。
   每輪最多問三個必要問題；文件已有答案的內容不要重複詢問。

2. 用我能理解的方式說明建議技術棧：
   包含每項工具的用途、選擇理由，以及目前是否可使用。
   技術方向為 React + Three.js（React Three Fiber）的 SPA。
   不必為了使用更多工具而增加複雜度。

3. 閱讀 https://github.com/mattpocock/skills 中準備採用的
   skill 指引，依需要使用：
   - grill-with-docs：釐清技術決策。
   - to-tickets：拆解實作工作。
   - implement：逐項完成實作。
   若無法使用，請說明並採取等效流程。
   任務與必要紀錄保留在本地專案，不建立遠端議題。

4. 讓我確認重要技術選擇後開始實作。
   先完成：
   開始遊戲 → 移動 → NPC 互動 → 第一個任務 → 顯示結果。

5. 第一條流程可以遊玩後，再逐步加入其他任務、
   結局、正式模型、UI、音效及背景音樂。
   初期可使用簡單幾何模型與暫代素材。

6. 需要 Blender、音訊生成或外部素材時，
   先確認工具能力與素材授權。
   無法直接操作的步驟，請明確引導我完成，
   不得將尚未製作或取得的素材說成已完成。

7. 每完成一段可玩功能，啟動預覽，告訴我：
   - 現在可以玩什麼。
   - 我要如何檢查。
   - 有哪些需要我決定的修改。

請持續推進到遊戲能從開始玩到結束，
本階段先在本地執行，部署留到第六階段。
```

**學生的參與：**確認技術方案、操作預覽、判斷玩法是否符合構想，並用具體描述提出修改，例如「接近 NPC 時提示太晚出現」，而不是只說「不好玩」。

### 第五階段：測試與修正

測試應在第四階段隨實作進行；第五階段則集中檢查完整流程、例外情況及玩家體驗。

**學生提示詞**

```text
現在開始第五階段：測試與修正。

請依前三份設計規格，檢查目前遊戲。
本階段直接執行測試與修正，不需要產出供我繳交的測試報告。

請閱讀並依需要採用 mattpocock/skills 中的：
- tdd：重要遊戲邏輯的測試。
- diagnosing-bugs：重現、定位、修正與複測。
- code-review：檢查程式品質與規格符合情況。

請執行：
1. 檢查遊戲能否正常啟動，模型與音檔是否載入成功。
2. 測試任務前置條件、完成條件、道具取得與消耗、
   重複互動、重複領獎、結局及重新開始。
3. 為重要規則建立有意義的自動化測試。
4. 工具支援時，用瀏覽器自動化走過主要遊玩流程。
5. 檢查 UI、鏡頭、碰撞、音量及靜音功能。
6. 依指定裝置與螢幕尺寸檢查顯示和操作。
7. 發現問題後，先重現與定位，再修正並重新測試。
8. 只把實際執行成功的測試標示為通過。

完成一輪後，啟動預覽，給我一份簡短的真人試玩清單。
等待我提供試玩結果，再修正影響操作與理解的問題。
也請引導我邀請一位同學自行試玩，觀察他卡住的位置。

請持續處理阻礙遊戲完成的問題。
結束時簡短告訴我：已通過哪些檢查、有哪些已知限制，
以及是否已具備部署條件。
```

**學生的參與：**親自走過完整流程，嘗試錯誤操作，觀察同學試玩，將「操作步驟、預期結果、實際結果」告訴 agent。

### 第六階段：部署與上線驗證

部署也是實作的一部分。不能只看部署工具顯示成功，還要從正式網址再次驗證遊戲。

**學生提示詞**

```text
現在開始第六階段：部署與上線驗證。

請先為專案加入 PWA 支援（vite-plugin-pwa）：設定 manifest 與圖示，
確認模型與音檔可離線使用，並在新版本發布時提示使用者重新載入。

接著檢查目前專案的建置方式與部署需求，
建議適合本專案的部署平台，說明：
- 是否支援目前技術。
- 是否需要帳號、公開儲存庫或付費。
- 網址與素材存取方式。
- 更新及回復上一版本的方法。

如果課程已有指定平台，優先使用：
Firebase Hosting；若有其他指定平台請填寫：【】

先完成所有可在本地進行的建置與檢查。
如需我選擇平台、登入帳號、確認公開範圍或處理費用，
請清楚說明需要我完成的步驟。
不要自行購買服務或公開與遊戲無關的檔案。

平台與公開方式確認後，請協助部署，並從正式網址檢查：
1. 首頁能否開啟。
2. 模型、貼圖、音效與背景音樂是否正常載入。
3. 任務能否完成、結局與重新開始是否正常。
4. 重新整理頁面後是否正常。
5. 離線模式能否開啟遊戲，是否可安裝為 App。
6. 指定裝置與瀏覽器的操作是否正常，手機是否有聲音。
7. 是否出現路徑、大小寫、網路或執行錯誤。

若發現問題，修正後重新部署並複測。
無法親自驗證的項目請明確告知，提供我可執行的檢查步驟。

最後直接提供：
- 正式遊戲網址。
- 簡短操作說明。
- 已知限制。
- 日後修改與重新部署的方法。

不需要另外製作階段報告。
```

這樣學生在第四至第六階段的重點就是：**指揮 agent 實作、親自驗證、根據結果修正，最後讓別人真正玩到遊戲。** 教師可以透過課堂操作與最終網址評量，不必增加中間文件作業。
